# ChainControl Upgrade Analysis

Audit date: 14 September 2026 (IST)

## 1. Purpose and scope

This document records the repository state before the enterprise inventory, governed NFT, observer, analytics, and administrative-decryption upgrade. It distinguishes functionality that is already implemented from functionality that is missing or only partially implemented so that subsequent phases extend the application without replacing working security controls.

At the time of this original audit, the repository contained one business React application, one Django REST backend, MySQL operational storage, Redis/Celery coordination, encrypted MinIO object storage, and one four-validator Hyperledger Besu QBFT network. That was a multi-validator permissioned blockchain simulation on one physical development machine. The later decentralization upgrade preserves those four as the initial set while adding dynamic enrollment and governed membership; see `DECENTRALIZATION_UPGRADE_PLAN.md` for current status.

## 2. Current architecture

```text
Browser
  -> NGINX :80
      -> React business application
      -> Django REST API / Django administration
          -> MySQL: users, workflows, projections, audit and indexed chain data
          -> Redis: Celery, DID proof tokens and signer nonce coordination
          -> MinIO: encrypted digital-asset ciphertext
          -> Web3.py: Besu JSON-RPC
              -> 4 QBFT validator containers on one host
                  -> TrustAccessManager
                  -> IdentityRegistry
                  -> AssetRegistry (OpenZeppelin ERC-721)
```

### Backend applications

| Application | Current responsibility |
|---|---|
| `accounts` | Custom user, departments, profiles, invitations, roles, permissions and administrator-issued wallet provisions |
| `identities` | DID records, identity-key history, signed one-time challenges and validator approval |
| `assets` | Unique physical/digital assets, encrypted versions, integrity checks and transfer requests |
| `blockchain` | Contract deployment projections, signed transaction submission, receipt/event indexing, reconciliation and basic health |
| `audit` | Searchable audit events and security alerts |
| `common` | UUID/timestamp base model, permissions, errors, middleware and read-only administration helpers |

### Runtime topology

`docker-compose.yml` already defines MySQL, Redis, MinIO, Django, Celery worker, Celery beat, React, NGINX, contract deployment tooling, a Besu bootstrap service and four independent Besu validator services. Each validator has a separate generated validator key and persistent data volume. All four participate in the same QBFT chain.

## 3. Functionality that already exists and should be reused

### Identity, accounts and RBAC

- Custom Django user and department-aware role assignments.
- Granular permission codes with department scoping.
- Explicit separation between Django superuser capability and platform permission assignments.
- Organization-issued encrypted controller-wallet provisioning with one-time claim codes.
- DID controller records and identity-key version history.
- One-time, purpose-bound signature challenges with replay prevention.
- Manual validator approval for pending identities and separation-of-duty checks.
- IST is already configured through `TIME_ZONE = "Asia/Kolkata"`; the React formatter displays `IST` explicitly.

### Blockchain and smart contracts

- `TrustAccessManager` uses OpenZeppelin `AccessControl` and grants distinct identity, access, mint, transfer, audit and emergency roles.
- `IdentityRegistry` stores a DID hash, controller, state and key version and emits lifecycle events.
- `AssetRegistry` is a real OpenZeppelin ERC-721 contract, not a MySQL simulation.
- Unique asset UUID hashes, content hashes, metadata hashes, token ownership and freeze state are stored on chain.
- Contract deployment metadata and ABI are imported into MySQL.
- All backend writes use one signer service with a Redis nonce lock and idempotency records.
- Celery tracks receipts, indexes known events and updates the operational projection only after confirmation.
- Ownership reconciliation compares MySQL with `ownerOf(tokenId)`, emits a security alert on mismatch and repairs only the derived projection.
- Four independent validator keys, data directories, processes and P2P identities are generated by the Besu bootstrap.

### Assets and storage

- Unique digital and physical asset records already exist.
- Digital content is encrypted with a fresh 256-bit AES-GCM data key per asset version.
- The data key is wrapped with the environment master key using a separate AES-GCM nonce.
- Asset UUID and version are authenticated as associated data.
- Only ciphertext is written to MinIO under `assets/<uuid>/versions/<version>.enc`.
- SHA-256 content and metadata hashes, wrapped-key material, nonces, MIME type and size are stored in MySQL.
- Retrieval authenticates AES-GCM and verifies the plaintext SHA-256 digest.
- Validator activation performs digital integrity verification and records an integrity check.
- Asset minting and governed transfer tasks submit real smart-contract transactions.

### Existing business transfer backend

- The backend implements request, recipient acceptance/rejection, independent approval, blockchain submission and post-event ownership projection.
- Sender and recipient cannot approve their own transfer.
- Department-scoped approval is supported.
- The current frontend only lists transfers and does not expose these actions.

### Administration and presentation

- Django administration has custom light/dark styling, read-only chain/asset/audit models and wallet provisioning.
- The React business application has login, overview, identity, asset registration, manual blockchain refresh, validator queues, wallet, audit, security and basic network pages.
- Client-side session restoration and route preservation are tested.

## 4. Existing behavior that is correct and must not be replaced

- Do not replace the central transaction, nonce and receipt-indexing path with frontend signing or MySQL-only state.
- Do not replace AES-GCM envelope encryption or use an asset UUID as encryption material.
- Do not place digital plaintext, private keys, wrapped plaintext keys or MinIO credentials on chain.
- Do not rewrite blockchain hashes after file tampering; preserve the mismatch as evidence.
- Do not replace blockchain-authoritative NFT ownership with a database-only implementation.
- Do not turn ordinary stock movements into individual blockchain transactions.
- Do not grant blockchain authority merely because an account is a Django superuser.
- Do not collapse the four validator containers into one validator.
- Preserve existing data with additive migrations and explicit data migrations.

## 5. Gaps and required changes

### 5.1 Inventory and catalogue: missing

There is no inventory application or model for categories, subcategories, dynamic catalogue items, variants, locations, quantity balances, movements, reservations or employee requests. The existing `Asset` model represents only unique physical/digital assets and cannot safely represent consumable stock or pooled software licenses.

Required addition: a new `inventory` Django application with dynamic catalogue and stock models, transactional movement services, employee/manager/admin/auditor permissions, REST endpoints, Django administration and business-app pages.

Recommended boundary:

- `Asset` remains the record for unique physical and unique digital assets that can be NFT-backed.
- `CatalogItem` and `CatalogVariant` describe reusable products dynamically.
- `InventoryStock` represents quantity at a location and department.
- `InventoryMovement` is the immutable quantity ledger.
- `InventoryRequest` and `InventoryReservation` implement employee request/approval/issue/return workflows.
- Pooled `SOFTWARE_LICENSE` quantities remain in inventory unless a specific license is deliberately modelled as a unique asset.

### 5.2 Asset-type separation: incomplete

`Asset.kind` currently has only `DIGITAL` and `PHYSICAL`. It needs a compatibility-safe representation of:

- `STOCK_ITEM`
- `UNIQUE_PHYSICAL_ASSET`
- `DIGITAL_ASSET`
- `SOFTWARE_LICENSE`

Stock items and pooled licenses should not become rows in `Asset`; they should be represented by the inventory module. Existing `PHYSICAL` rows must map to `UNIQUE_PHYSICAL_ASSET`, and existing `DIGITAL` rows must map to `DIGITAL_ASSET` without destructive renaming. An additive `asset_type` field plus data migration is safer than immediately removing `kind`.

### 5.3 Mint authorization: requirement mismatch

The current `USER` role receives `asset.mint`, and the business UI exposes asset registration to any account with that permission. This contradicts the requested Admin/`ASSET_MINTER`-only policy.

Required change:

- Remove `asset.mint` from the default User role.
- Restrict unique-asset registration/mint submission to the intended Admin role and appropriate department scope.
- Retain independent smart-contract `ASSET_MINTER_ROLE` enforcement.
- Add negative API and contract integration tests.

### 5.4 Governed ERC-721 transfer: security mismatch

Although `governedTransfer` is role-restricted, inherited ERC-721 `transferFrom` and `safeTransferFrom` currently remain usable by the token owner while the asset is active. The existing contract test explicitly expects direct owner transfer. This bypasses recipient acceptance and manager approval.

Required change: restrict non-mint/non-burn token movement so only the authorized transfer agent can execute it, while preserving standard ERC-721 ownership and `Transfer` events. Update tests to prove direct owner transfer fails and approved `governedTransfer` succeeds.

### 5.5 NFT lifecycle and semantics: partial

Real minting, ownership, proof, freeze and transfer exist. Missing pieces include explicit unfreeze/archival events and backend/UI lifecycle operations, richer human-readable NFT endpoints, transfer-count/history projection, and a read-only explorer. The event indexer currently covers only a fixed list and does not independently backfill arbitrary block ranges.

### 5.6 Business frontend: partial

The current React application is concentrated in `frontend/src/App.tsx`. It lacks:

- Inventory, hardware, software, catalogue, availability and request screens.
- Role-scoped catalogue and stock controls.
- My Requests and My Assigned Assets.
- Transfer create/accept/reject/approve controls.
- Rich NFT ownership and history presentation.

The existing theme and authentication/wallet flows should be retained. The application should be decomposed into features/pages as it grows rather than expanding the monolithic file indefinitely.

### 5.7 Blockchain observer: missing

There is no second observer application. The current `/network` page only shows basic validator reachability and height, while transaction/event pages are generic lists.

Required addition:

- A second read-only React application, exposed separately (development target `localhost:5174`, Compose/NGINX port documented explicitly).
- Backend observer APIs sourced from Besu for blocks, transactions, receipts and logs, enriched with ABI decoding and permission-safe MySQL context.
- Incrementally loaded vertical block visualization, block/transaction details, search, NFT explorer, analytics and actual validator topology/health.
- Efficient polling initially if WebSocket subscription is not practical; no fabricated blocks, metrics or node status.

### 5.8 Observer backend and chain indexing: missing/partial

Current blockchain APIs expose only indexed transaction/event lists and basic health. They do not expose raw blocks, parent hashes, transaction receipts, gas, proposer, peer count, consensus status, decoded inputs, cross-source search or paginated chain traversal.

Required changes are concentrated in `backend/apps/blockchain/`: observer serializers/services/views, ABI decoding, block pagination, search, richer health, safe enrichment and tests. Besu should remain the authoritative source of block history.

### 5.9 Analytics: missing

There is no analytics service or chart UI. Aggregate APIs must query real inventory, asset, identity, role, audit and blockchain data. Charts must not contain fixtures or hardcoded values.

### 5.10 Administrative decryption utility: absent

The requested specification states that a Python decryption utility exists, but repository-wide inspection found no such script or management command. Only the internal `retrieve_and_verify()` function exists. Therefore, there is no existing CLI workflow to preserve.

Required addition: an authenticated/attributed Django management command that accepts an asset UUID and mandatory reason, uses the existing authenticated retrieval path, verifies the hash, writes to an explicitly selected controlled output, applies restrictive file permissions where supported, records success/failure audit evidence without secrets, and supports explicit cleanup without surprising deletion.

Development currently combines MinIO administration and decryption authority through access to application secrets. Production documentation must explicitly require KMS/HSM separation.

### 5.11 Validator health: partial

All four nodes exist, but health currently reports only RPC connection and block height. It needs actual peer count, QBFT validator membership/consensus data, latest block agreement and dynamic offline reporting. Organizational labels are presentation metadata only; every validator participates in the same consensus.

### 5.12 Documentation status: stale

Several documents still state that Docker was absent and live Compose verification had not occurred, although Docker has since been installed and the four-node network has been run. Documentation must be reconciled with executed evidence and must distinguish implementation from testing.

## 7. Migration risks and mitigations

| Risk | Mitigation |
|---|---|
| Existing physical/digital records are reclassified incorrectly | Add a nullable/additive type, run deterministic data migration, validate counts, then enforce non-null |
| Stock becomes negative under concurrent requests | Use `transaction.atomic()`, `select_for_update()`, database constraints and service-only mutations |
| Cached quantity diverges from movement history | Treat movements as immutable evidence and update balances in the same locked transaction |
| Contract upgrade invalidates the current deployment address | Deploy a new version, import ABI/address as the active deployment, retain old deployment metadata and document local-chain reset/migration strategy |
| Existing NFTs remain in an older contract | Do not pretend they migrated; provide an explicit development redeploy/remint plan and a production migration plan |
| Direct ERC-721 calls bypass approval | Enforce transfer-agent authorization inside the contract movement hook and test all transfer variants |
| Observer leaks PII or secrets | Permission-gate observer APIs, whitelist enrichment fields and never serialize wallet, MinIO or encryption secrets |
| Block history overwhelms the client | Descending cursor/page APIs, bounded transaction previews, lazy detail fetching and list virtualization |
| Decryption creates unmanaged plaintext | Require an explicit destination/reason, restrictive permissions, clear output reporting and optional explicit cleanup |
| Audit writes fail during recovery | Fail closed or clearly report audit failure; never silently decrypt without evidence |
| Four nodes on one host are misrepresented | Consistently label the setup as a single-host multi-validator simulation |

## 8. Compatibility constraints

- Existing account IDs, DIDs, wallet provisions, asset UUIDs, MinIO object keys and audit records must remain valid.
- Existing API routes should remain compatible where possible; new response fields should be additive.
- Existing `Asset.kind` consumers require a transition period if `asset_type` is introduced.
- Observer access must not grant mutation permissions.
- The business application must remain usable through `http://localhost/` while a separate observer endpoint is added.
- MySQL remains the operational system of record for stock and workflow; Besu remains authoritative for NFT ownership and critical on-chain state.

## 9. Implementation phases

1. **Audit baseline** — this document, baseline tests and schema/runtime inventory.
2. **Inventory model and services** — dynamic catalogue, locations, balances, movements, reservations, requests, locking, migrations and backend tests.
3. **Inventory APIs and main UI** — employee browsing/requesting, manager approval/issue and Admin catalogue/stock controls.
4. **NFT policy hardening** — Admin-only mint permission, governed-transfer enforcement, lifecycle events and contract/backend tests.
5. **NFT business UI** — NFT metadata, ownership, transfer lifecycle and assigned assets.
6. **Observer backend** — block/transaction/receipt/log APIs, ABI decoding, search, NFT enrichment, analytics and richer validator health.
7. **Observer frontend** — scrollable real chain, detail views, NFT explorer, analytics and network visualization.
8. **Decryption hardening** — audited management command, controlled output and failure tests.
9. **End-to-end validation and documentation** — Docker integration, live four-validator/offline-node checks, demonstration scenario and truthful status updates.

Minor ordering adjustments are acceptable where migrations or shared APIs are prerequisites, but incomplete work must remain labelled incomplete.

## 10. Test plan

### Inventory

- Catalogue/category/variant creation permissions.
- SKU uniqueness and indexed lookup.
- Stock-in/out/reserve/release/issue/return/transfer/adjust arithmetic.
- Database constraints and locked concurrent reservation tests proving no oversell.
- Employee visibility and request lifecycle.
- Manager department scope and Admin-only catalogue controls.
- Immutable movement and audit evidence.

### Contracts and NFT integration

- Authorized governance mint succeeds; unauthorized account and normal User API mint fail.
- Duplicate UUID mint fails.
- Direct `transferFrom` and both `safeTransferFrom` variants cannot bypass governance.
- Approved governed transfer succeeds and emits standard plus semantic events.
- Frozen/archived assets cannot transfer.
- Owner, token, content hash and metadata hash match the MySQL projection.
- Event indexing and reconciliation operate against the deployed contract.

### Observer

- Blocks come from Besu and are ordered with correct hash/parent-hash linkage.
- Transaction count and indices match block data.
- Receipts, gas, status, input parameters and events decode through the deployed ABI.
- Searches resolve block number/hash, transaction hash, address, DID, asset UUID and token ID.
- Pagination is bounded and stable with large histories.
- NFT owner and history match on-chain state.
- Health reports four real nodes and detects a deliberately stopped node.
- Observer endpoints reject mutation and filter sensitive context.

### Decryption

- Valid digital asset UUID decrypts and verifies.
- Invalid UUID, physical asset, missing version and missing object fail clearly.
- Wrong wrapped key and modified ciphertext fail AES-GCM authentication.
- Plaintext SHA-256 must match the stored authoritative digest.
- Success and failure audits contain actor, reason, timestamp, result, object and request ID but no keys.
- Output permissions and explicit cleanup behavior are tested.

### Regression

- Authentication, wallet provisioning, DID challenge/replay prevention and validator separation remain intact.
- Existing backend, frontend and contract tests continue to pass after intentional policy-test updates.
- Migrations run from the current schema without deleting data.
- React production builds succeed for both applications.
- Complete Docker Compose startup, contract deployment/import and business/observer smoke tests succeed.

## 12. Phase-A decision

The repository is a solid security-focused vertical slice, not an empty scaffold. Inventory, observer and analytics should be additive modules. The real ERC-721, four-validator network, encryption, wallet issuance, DID proof, transaction service, event indexing and reconciliation should be retained and hardened at their identified policy boundaries.
